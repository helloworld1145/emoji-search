## 用户需求

- 在搜索页输入收藏夹名称时，搜索结果中直接出现该收藏夹内的表情包。
- 用户已明确：「只合并表情，不显示收藏夹入口」——即不做「收藏夹」结果区块、不做跳转收藏夹详情的入口，仅把名称匹配的收藏夹内的表情合并进表情搜索结果。

## 产品概述

表情包管家（Vue 3 + Capacitor Android App）的搜索页当前仅支持按表情包上的文字/标签/情感搜索。本次扩展为：关键词命中收藏夹名称时，把该收藏夹内的表情合并进搜索结果网格。

## 核心功能

- 关键词命中收藏夹名称时，将收藏夹内表情合并进搜索结果网格（文字/标签命中结果在前，收藏夹命中表情追加在后）。
- 合并结果按表情 id 去重；统一过滤已软删表情（deleted_at = 0）。
- 搜索框 placeholder 与初始空状态文案更新，提示支持按收藏夹名称搜索。
- 搜索历史点击、300ms 防抖输入等既有交互自动复用新逻辑，无额外改动。
- 边界：同一表情同时命中文字与多个收藏夹时按 id 去重；空收藏夹贡献 0 个表情；结果总量设上限（约 240）防止膨胀；收藏夹查询失败时降级为仅文字结果，不阻塞主流程。

## 技术栈

- 前端：Vue 3 + TypeScript + Vite（既有栈，无新增依赖）
- 数据层：既有 @capacitor-community/sqlite 仓库模式，参数化查询（Web 端 jeep-sqlite 兜底）
- 路由：既有 Vue Router（本次不新增路由，不跳收藏夹详情）

## 实现方案

采用「编排层合并」策略：既有 `emojiRepo.search()`（文字/标签/情感 LIKE 查询）保持稳定不改；在收藏夹仓库新增一条 JOIN 查询按收藏夹名称取表情；在 `Search.vue` 的 `runSearch()` 中先后执行两次查询，按 id 去重合并。避免改动既有搜索 SQL，回归面最小。

关键决策：

1. 复用 `toRecord`：`emoji.ts` 的 `toRecord`（第 142 行）当前为模块私有，`EmojiRow`（第 122 行）亦未导出。将二者导出，供 `collection.ts` 复用，避免该文件再手写一份 row→EmojiRecord 映射（其 `getCollectionItems` 已有重复映射前科）。导出本身零行为变化。
2. SQL 全部参数化：`c.name LIKE ?`，遵循项目「参数化查询」约定；查询统一带 `e.deleted_at = 0`，符合 CODEBUDDY.md §5 红线（所有 emojis 读查询必须过滤软删）。
3. 单条 JOIN 完成匹配：不再走「先查收藏夹列表再逐个取表情」两段式流程，一次查询返回全部命中收藏夹内的表情。

## 性能与可靠性

- 每次搜索固定 2 次查询（文字 LIKE + 收藏夹 JOIN LIKE），防抖 300ms 已有；千级数据量下 LIKE + 现有索引足够，无 N+1。
- 合并去重在内存完成，复杂度 O(n)；上限 240 截断防结果膨胀。
- 收藏夹查询异常不阻塞文字结果（降级路径）；SQL 全参数化，无注入风险。
- 无数据库 schema 变更、无原生改动、不加新依赖，不涉及真机回归。
