## 用户需求

真机（Android 16）安装 debug 包后，选择表情包文件夹无法识别到图片，第一轮修复无效。需重新定位根因并修复，最后重新打包 debug 包供真机验证。

## 产品概述

让「手动选择文件夹扫描表情」功能在真机上可靠工作：选择文件夹后能正确枚举其中的图片、显示缩略图并完成 AI 识别；且**任何失败原因都能在界面上被用户看到**，不再出现"点了没反应、完全没提示"的静默体验。

## 核心功能

### 1. 失败原因可见（最高优先级）

- 扫描失败时首页明确显示红色警示条与具体失败原因（区分"目录授权失败""读取被系统拒绝""未找到图片"等），不再静默无响应。
- 选择文件夹被取消时静默返回；选择失败（授权异常）时明确提示，与"扫描失败"区分开。
- 提示内容携带真实的底层错误码/错误信息，便于定位。

### 2. 图片枚举健壮性修复

- 修复"系统返回空结果时直接放弃"的缺陷；改为双通道枚举（系统文档接口优先、文件接口兜底），任一通道成功即可入库。
- 当系统枚举到文件但因格式判定被全部过滤时，诊断信息能反映真实原因。

### 3. 目录授权兼容性

- 修复 Android 15 及以上系统上目录授权持久化参数不完整导致的授权失败。

### 4. 交付验证

- 输出新的 debug 安装包，并提供明确的真机验证步骤与日志抓取方法。

## 视觉表现

沿用现有卡片式与配色体系：扫描中为蓝色渐变进度条；成功为绿色对勾条；新增失败态为红色警示条（含警示图标 + 具体原因文案），位置与既有进度条一致，不引入新组件或新页面。

## 技术栈

沿用现有技术栈，不引入任何新依赖：Android 原生（Java，Capacitor 6 插件）+ Vue 3 + TypeScript + Pinia + Tailwind CSS。

## 根因重新定位

上一轮把问题假设为「`scanFolder` 枚举返回 0 张」，本轮依据用户新提供的决定性事实——**"触发扫描后 App 完全没有提示"（无 toast、无"扫描完成"、无进度条）**——重新排查。该现象推翻了上一轮假设，因为代码链路中：

- 扫描成功必然产生可见反馈：`startFolderScan` 成功时置 `phase='done'`，`ScanProgress` 渲染"扫描完成，共 N 张表情"。
- 点首页「选择文件夹」时，picker 一旦成功必然弹 toast：`Home.vue:95-104` 的 `onPickFolder` 拿到非空 `f` 就弹 `已扫描：xxx`。

因此"无任何提示"只可能来自两个被静默吞掉的失败点，已逐行核实：

### 缺陷 A：`ScanProgress.vue` 缺少 error 分支（已核实）

`src/components/ScanProgress.vue:15-17`

```ts
const visible = computed(() =>
  ['scanning', 'recognizing'].includes(props.state.phase)
)
```

`visible` 只含 `scanning` / `recognizing`，模板仅有 `v-else-if="state.phase === 'done'"` 分支，**全文没有渲染 `phase === 'error'` 的分支**。而 `src/stores/emoji.ts:124-132` 的 `startFolderScan` catch 分支明确会置 `phase='error'`、`message='文件夹扫描失败，请重试'`——该状态被 UI 完全丢弃。

### 缺陷 B：`addFolder()` 静默吞掉异常（已核实）

`src/services/scanner.ts:126-134`

```ts
export async function addFolder(): Promise<SavedFolder | null> {
  try {
    const res = await EmojiScanner.openFolderPicker()
    return { treeUri: res.treeUri, name: res.name }
  } catch (e) {
    // 用户取消选择会 reject（如 FOLDER_PICK_CANCELLED），视为正常取消
    return null
  }
}
```

catch 内**连 `console.error` 都没有**，把"用户主动取消"与"授权真实失败"混为一谈，全部归为 `null`；`addFolderAndScan` 据此提前 return，`onPickFolder` 的 `if (f)` 不成立，扫描根本未开始且界面无任何反馈。

### 缺陷 C：第一版修复的兜底漏洞（已核实）

`FolderScannerUtil.java:82-93` 仅当 `children == null` 时回退 `DocumentsContract` 显式查询；**返回空数组（`length == 0`）时被直接当作"空目录"跳过**，兜底根本不触发。真机上 `listFiles()` 返回空数组是常见现象，这是第一版修复"改了仍然 0 张"的原因之一。

### 缺陷 D：Android 15+ 持久授权掩码不完整（已核实）

`FolderStore.java:41-42`

```java
ctx.getContentResolver().takePersistableUriPermission(
    uri, Intent.FLAG_GRANT_READ_URI_PERMISSION);
```

仅传 READ 掩码。Android 15+（API 35/36）要求同时具备 READ|WRITE 掩码，否则可能抛 `SecurityException`——而该异常当前被 `catch` 吞成 `Log.w`。`releasePersistableUriPermission`（第 75-76 行）同样只传 READ。`openFolderPicker` 的 intent flags 已含 READ|WRITE|PERSISTABLE，无需改动。

## 实现方案

### 1. 打通诊断链路（先让问题可见，再谈修复）

采用「错误信息透传 + 分类提示」策略，避免继续盲猜：

- **`ScanProgress.vue`**：`visible` 保持不变，另加 `v-else-if="state.phase === 'error'"` 分支，渲染警示图标（`AlertCircle`）+ `state.message`，配色沿用既有 `text-danger`/`bg-danger` 体系（Tailwind 已有 `danger` 色，见 `Home.vue:349` 使用），不新增组件、不改布局。
- **`stores/emoji.ts` `startFolderScan`**：catch 中把 `e` 的真实信息带进 message（如 `文件夹扫描失败：${msg}`），并保留 `console.error`。这样原生 reject 的错误码（如 `FOLDER_SCAN_FAILED`）会直接显示在界面上。
- **`scanner.ts` `addFolder()`**：区分两类失败——`FOLDER_PICK_CANCELLED` 视为正常取消返回 `null`（不打扰用户）；其余异常 `console.error` 并向上抛出，由调用方展示。
- **`stores/emoji.ts` `addFolderAndScan`**：捕获上抛的真实异常并写入 `scanState`（`phase:'error'`），使首页警示条能显示。
- **`Home.vue` `onPickFolder`**：picker 成功但 `f` 为空时不再静默，补一个提示。

### 2. 修复枚举兜底漏洞（双通道策略）

`FolderScannerUtil.walk` 的兜底条件从 `children == null` 改为 **`children == null || children.length == 0`**。

更进一步：将**主路径与兜底路径对调**——先走 `DocumentsContract.buildChildDocumentsUriUsingTree` 显式查询（可直接拿到 `document_id`/`mime_type`/`display_name`/`size`/`last_modified`，行为可控且能规避 `DocumentFile` 在部分 ROM 上的空结果），失败或返回空时再回退 `DocumentFile.listFiles()`。理由：`DocumentFile` 只是 `DocumentsContract` 的一层薄封装，显式查询能拿到更完整的信息（尤其 mime），既利于过滤也利于诊断；两条通道覆盖同一目录，任一成功即可避免"假空"。

同时**增强诊断**：在 `queryChildren` 中统计并输出被扩展名规则过滤掉的条目数与前若干条的 `name`/`mime`，用于判断"枚举到了但全被过滤"这类静默归零场景（这是除权限外的另一类可能根因，目前完全不可见）。

保持既有的扩展名白名单、目录跳过规则（`.` 开头 / `Android` / `LOST.DIR`）、`WALK_LIMIT` 与单线程 executor 分页结构不变，不改动 `scanner.ts` 的循环分页与入库编排，不动数据库表结构。

### 3. 修复 Android 15+ 授权掩码

`FolderStore.add` / `FolderStore.remove` 的掩码统一改为 `Intent.FLAG_GRANT_READ_URI_PERMISSION | Intent.FLAG_GRANT_WRITE_URI_PERMISSION`，并把失败日志提升为 `Log.e` 以便定位。注意保持 add/remove 掩码一致，避免释放时抛异常。

## 实施注意事项

- **日志与隐私**：沿用现有 `Log.i/d/w/e` + TAG 惯例；`FolderScannerUtil.safeLog` 已只输出 authority + 末段，新增日志沿用该方式，不打印完整文件路径或完整 URI。
- **改动半径**：第一轮成果（诊断日志、`DocumentsContract` 兜底、`getViewableUrl`、`copyToCache`、`toImageSrcAsync` 组件改造）全部保留，仅在其上做增量修正，不回退。
- **兼容性**：Web（Mock）模式不受影响，`addFolder` 的错误分类对 Mock 同样适用。
- **日志级别**：定位用的 `Log.i/d` 在问题确认后可降级为 `Log.d`，本轮先保留以便用户复现后回传日志。

## 关键改动契约

`ScanProgress` 的 error 态数据契约（复用现有 `ScanProgress` 类型，无需新增字段）：

- `phase`: `'error'`
- `message`: 携带真实原因，如「文件夹扫描失败：FOLDER_SCAN_FAILED」
- 渲染：`visible` 不含 `error`，由 `v-else-if="state.phase === 'error'"` 分支承接

## 打包与验证

打包顺序：`npm run build` → `npx cap sync android` → `cd android; .\gradlew.bat assembleDebug --console=plain`，产物位于 `android/app/build/outputs/apk/debug/app-debug.apk`。
